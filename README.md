# 🍱 惜食整合系統 — 演示與開發說明 (Food Rescue Demo System)

本專案是一個零預算、完全基於本地端與未來 Serverless 架構設計的**「O2O 惜食地圖導購與智慧物聯扭蛋機」**系統演示原型。

此系統結合了以下兩大情境：
1. **惜食地圖導購**：消費者可以透過手機瀏覽 Leaflet 惜食地圖，尋找附近店家的折扣惜食，進行模擬付款並產生取餐碼，再前往實體店面核銷取餐。
2. **物聯網智慧惜食扭蛋機**：安裝於實體機台上的平板展示端（Kiosk），能以盲盒/扭蛋的趣味形式將各店惜食進行隨機抽獎，並透過物聯網（ESP32 + MQTT）在消費者付款並轉動物理旋鈕後，自動開啟實體艙門。

---

## 🚀 快速啟動

專案已配置好所有本地依賴與資料庫，只需簡單指令即可啟動：

### 1. 啟動本地開發伺服器
於專案根目錄執行：
```bash
npm run dev
```

伺服器將在 `http://localhost:3000` 啟動，並自動載入記憶體/本地 SQLite 資料庫與種子測試資料：
- **API 健康檢查**: [http://localhost:3000/api/health](http://localhost:3000/api/health)
- **📱 手機端 (Mobile Web PWA)**: [http://localhost:3000/mobile/](http://localhost:3000/mobile/)
- **📺 平板端 (Tablet Vending Kiosk)**: [http://localhost:3000/tablet/](http://localhost:3000/tablet/)

### 2. 登入測試帳號
- **消費者 (Consumer) 帳號**: 
  - 信箱：`consumer@test.com`
  - 密碼：`test1234`
- **店家 (Store Owner) 帳號**:
  - 信箱：`store@test.com`
  - 密碼：`test1234`

## 🗺️ 運作流程與功能演示指南

### 路徑一：手機端「地圖導購」全流程
1. 瀏覽器開啟 [http://localhost:3000/mobile/](http://localhost:3000/mobile/)
2. 登入消費者帳號 `consumer@test.com`。
3. 進入 **惜食地圖**，網頁將載入 Leaflet.js 地圖並在地圖上顯示附近惜食商品的 Pin 針（🍱/🍞/🥬）。
4. 點擊地圖上的 Pin 針或點擊「立即購買」，進入店家商品詳情。
5. 點擊「購買」，進入確認付款頁。
6. 點擊「模擬付款」，付款完成後會顯示該訂單的 **4 碼取餐代碼**（例如 `A7B9`）。
7. **店家核銷**：登出消費者，登入店家帳號 `store@test.com`，進入「訂單核銷」頁面，輸入消費者的 4 碼取餐代碼，確認後該商品將標記為 `SOLD`，訂單完成！

### 路徑二：平板端 + 手機端「物聯網扭蛋」全流程
1. 用平板或新瀏覽器分頁開啟智慧機台展示端：[http://localhost:3000/tablet/](http://localhost:3000/tablet/)。
2. 畫面會顯示目前機台 `MAC_01A2B3` 的 6 個艙位狀態（預設艙位 1~2 有食物，艙位 3~6 為空）。
3. 點擊「開始扭蛋」，選擇想排除的過敏原（例如：海鮮、花生）。
4. 點擊「確認」，機台會向後端請求建立抽獎訂單，並在畫面上生成該筆訂單的**模擬付款 QR Code**。
5. **消費者付款**：用手機端（登入 `consumer@test.com`）點擊訂單頁面，或是模擬掃描平板 QR Code，會進入手機付款頁面。點擊「模擬付款」後，手機端提示付款成功。
6. **物理觸發**：此時平板端會感應到付款狀態，轉為「請轉動旋鈕！」動畫畫面。
   - *提示*：在真實場景中，消費者此時轉動 ESP32 機台上的 KY-040 旋鈕，ESP32 會發送 HTTP POST `/api/v1/machines/trigger` 請求給伺服器。
   - *測試模擬*：您可以使用終端機，執行以下 `curl` 指令來模擬 ESP32 傳送旋鈕轉動信號：
     ```bash
     curl -X POST http://localhost:3000/api/v1/machines/trigger -H "Content-Type: application/json" -d "{\"machine_id\":\"MAC_01A2B3\",\"action\":\"KNOB_TURNED\",\"secret_key\":\"dev_secret_key_001\"}"
     ```
7. 後端收到觸發信號後，會根據消費者的過敏原自動從商品池中隨機抽取一份，更新資料庫，並透過 MQTT 發送開門指令給對應艙位門鎖。
   - **後端 Console 輸出**：您會在啟動伺服器的終端機中，看到類似 `[MQTT Mock] 發送開門指令給機台 MAC_01A2B3, 艙位 index: 1, 訂單 ID: order_X` 的日誌，這代表 MQTT 協議工作正常！
8. **開獎動畫**：平板端輪詢到結果後，會播放 GSAP 滾動輪播抽獎動畫，最終停在被抽中的艙位，並爆出七彩碎紙特效（Confetti），顯示開門成功與獲得的點數！

### 店家端：機台配對與艙位補貨管理
1. **機台配對**：在平板展示端點擊左下角的「店家配對」，會產生一個配對專屬 QR Code。
2. **手機掃碼確認**：登入手機端店家帳號 `store@test.com`，進入「配對機台」，手機會啟動相機掃描平板上的 QR Code（或點擊確認連結）。配對完成後，手機端會出現機台管理後台。
3. **艙位補貨**：在手機端機台後台，店家可以看到 6 個艙位。若某艙位為空（`EMPTY`），店家可點擊「放入商品」，選擇店家自己上架的商品。
   - 後端會發送 MQTT 指令開啟對應艙門（模擬 Console 印出 `[MQTT Mock] 發送開門指令...` 讓店家放食物）。
   - 食物放入後，該艙位在手機端與平板端會同步顯示為 `STOCKED` 狀態，成功完成補貨！

## 🔒 系統防呆與安全性設計 (本地原型)
1. **API Cooldown 機制**：ESP32 觸發設有硬體防彈跳 (Debounce 500ms) 與軟體 Cooldown (2000ms)，避免惡意刷獎。
2. **自動退款與艙位釋放**：若訂單建立並付款後，消費者於 5 分鐘內未轉動旋鈕（例如付款後直接離開），伺服器內置定時排程會將訂單標記為超時退款，並將預留的機台艙位重新釋放為 `STOCKED`，防範佔位。
3. **過敏原極致篩選**：抽獎演算法採用資料庫即時過濾，如果篩選後的商品池為空（例如機台裡只有花生麵包，但消費者排除了花生），系統會在訂單建立階段直接拒絕並提示，防止消費者付款後抽不到食物。
